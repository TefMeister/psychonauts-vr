| 2026-09-03 | [The level format has no entity parenting — so any parent is runtime-only](topics/2026-09-03-the-level-format-has-no-entity-parenting-so-any-parent-is-runtime-only.md) | ✅ incorporated | **✅ Folded 2026-09-03 as a narrowing: the informative `headpos` states are moving platform / levitation ball / grabbed.** ⭐ The other half of the `+0xB8` question, and it needed no launch. `DomainEntityInfo` places every entity by absolute **`Position`/`Rotation`/`Scale`** and carries **no parent, attach-entity or attach-bone field**; `Domain` has `Children` but **no parent back-reference and no transform**; `EntityInitData` holds only line collision. So no entity can arrive from the level file already parented — **any non-null `+0xB8` is assigned at runtime**, which is exactly the code surface the 2026-09-02 `.text` scan swept and found clean. | 2026-09-03 | [PVS leaf size is absent from the format — but two numbers in any `.plb` would bound it](topics/2026-09-03-pvs-leaf-size-is-absent-from-the-format-but-two-numbers-in-any-plb-would-bound-it.md) | ✅ incorporated | **✅ Now the board's `[PD]` row — but ⚠️ my cost was wrong: zero loose `.plb` files, levels ship as 50 `PPAK` (`.ppf`) containers. See the 2026-09-03b row for the tools that open them.** Yesterday's *"first person is probably safe from the PVS gate"* rests on an unchecked assumption — that leaves are large next to the eye offset. The octree is **regular**: `OctreeNode` is eight packed octants with `IsLeafFlag = 0x00400000`, `OctreeLeaf` stores only a primitive index/count and **no bounds**, and there is no max-depth or threshold constant — so leaf extent = root `SSECube` / 2^depth, baked by Double Fine's tooling. Therefore **the root cube extent + `LeavesCount` from one real level bound it**, statically, off a file already on disk. Few hundred leaves ⇒ room-scale, FP safe; many thousands ⇒ an FP camera may change leaf and popping-on-engage is a PVS symptom, not a matrix bug. Flags a licence judgement call (parse the two fields ourselves vs. use a GPL tool as a tool) as the modding lane's to make. |
| 2026-09-03 | [Nobody documents Psychonauts' world scale — and there is a reason](topics/2026-09-03-nobody-documents-psychonauts-world-scale-and-there-is-a-reason.md) | 🆕 new | **A confirmed negative, deliberately recorded so it stops being re-searched.** Checked PsychoPortal, Jill Crungus's RE blog (including the *Making Levels* custom-level guide — the one place a "one unit is this big" statement would have to appear when importing outside geometry), the Oatmeal `.plb`→glTF converter and Blender workflow, and the community format tools: **no unit convention anywhere**. The structural reason: the community pipeline is a **round trip in native units** (`.plb`→glTF→Blender→glTF→`.plb`), which never needs a metres conversion, so nobody ever had cause to establish one `[hypothesis]`. Consequence for `fpheight`: the live `headpos − playerpos` measurement will have **no external cross-check**, so build the check in — take it `n>1` on confirmed-level ground (not the parking lot, where Raz's Y moved 113.04 → 139.35 → 84.72 in one short walk) and sanity-check against the in-engine yardsticks already on record. |
| 2026-09-02 | [The level format ships a precomputed visibility set — so there are two culling gates, not one](topics/2026-09-02b-the-level-format-ships-a-precomputed-visibility-set-so-there-are-two-culling-gates.md) | 🆕 new | ⭐ PsychoPortal's source shows `Scene/VisibilityTree` = an **octree + one bit-buffer per leaf sized from `LeavesCount − 1`** — one bit per other leaf, the classic from-region **PVS** — and it is **separate** from `CollisionTree` and `NavMesh`.
